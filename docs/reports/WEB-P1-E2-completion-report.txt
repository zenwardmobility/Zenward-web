1. CONTACT DELIVERY IMPLEMENTATION
================================================================================

A real ContactIntakeAdapter was implemented, provider-isolated:

  src/lib/contact-intake/adapter.ts
    - ContactIntakeAdapter interface (unchanged seam)
    - StubContactIntakeAdapter   (default) — acknowledges, delivers nothing,
                                  stores nothing, logs no message content,
                                  touches no credential.
    - EmailContactIntakeAdapter  — sends a plain-text internal enquiry via the
                                  Resend REST API (https://api.resend.com/emails)
                                  using a single fetch(). No SDK dependency, so
                                  the provider surface is one function and is
                                  swappable. 10s timeout.

Selection: CONTACT_INTAKE_MODE = "stub" (default) | "email".

Delivery format (email mode):
    Subject: "New Zenward Website Enquiry — <topic label>"
    Body (plain text) contains ONLY: reference id, topic, name, email,
    phone (if given), organization (if given), and the message.
    reply_to is set to the enquirer's email. No technical metadata.

Credentials / destination are server-only environment variables, never
NEXT_PUBLIC_, never sent to the browser:
    CONTACT_INTAKE_EMAIL   — internal inbox that receives enquiries
    CONTACT_EMAIL_FROM     — verified Resend sender
    CONTACT_EMAIL_API_KEY  — Resend API key

If mode=email but any of the three is missing, the adapter fails closed and
returns a non-technical "we couldn't send your message just now, please try
again or call us" message; it logs only that the vars are unset (no content).

Current production behaviour: CONTACT_INTAKE_MODE is unset ⇒ stub. Enabling
real delivery is env configuration only (see section 5 / launch-readiness).

2. REQUEST INTAKE STATUS
================================================================================

Architecture preserved exactly:
    Browser  →  Server Action (src/app/request-transportation/actions.ts)
             →  validation (whitelist rebuild + normalise + caps + enums + guard)
             →  RequestIntakeAdapter (src/lib/request-intake/adapter.ts)
             →  [ destination ]

Adapters:
    StubRequestIntakeAdapter (default)
        - Validates and acknowledges. Delivers NOTHING. Stores nothing.
        - Returns { ok: true, delivered: false, referenceId }.
        - In production, logs one line: "running in STUB mode: ... NOT
          delivered anywhere" — NO request payload, ever.
    PlatformRequestIntakeAdapter (implemented, not yet reachable)
        - Signed server-to-server POST (Bearer token, 10s timeout) of the
          validated payload to the Platform's trusted intake endpoint.
        - Requires PLATFORM_INTAKE_URL + PLATFORM_INTAKE_TOKEN (server-only).
        - If selected without them: fails closed with an honest "online
          requests are temporarily unavailable, please call us" message —
          it never fakes a successful delivery.
        - A 2xx response ⇒ { ok: true, delivered: true }.

Selection: REQUEST_INTAKE_MODE = "stub" (default) | "platform".
The Platform API URL was NOT invented.

Honesty guarantee (verified in-browser): in stub mode the success screen does
NOT say "Zenward will contact you". It says the details are received and the
visitor should also call to confirm, and shows a "Call 470-206-8005" button.
Only delivered === true shows the "Zenward will review and contact you" copy.

What is NOT done (by design): no Supabase connection, no anonymous DB access,
no email delivery of transportation-request content, no full-payload logging,
no browser-storage persistence, no request content to analytics.

4. FORM SECURITY CHANGES
================================================================================

New shared module: src/lib/forms/guard.ts (server-side only).

Both Server Actions now:
    - Accept the payload as `unknown` and REBUILD it from a fixed field
      whitelist — any unexpected properties the client sends are dropped.
    - Normalise every string: strip C0/C1 control chars (keep tab/newline),
      collapse runaway blank lines, trim, truncate to a per-field cap
      (name 120, email 254, phone 40, org 160, short text 400, long text 2000).
    - Validate enum/select fields against their allowed literal values
      (relationship, return-trip, contact topic).
    - Reject a total JSON payload larger than 16 KB before touching an adapter.
    - Honeypot: hidden off-screen field `company_website`
      (src/components/public/FormHoneypot.tsx, aria-hidden, tabIndex=-1);
      non-empty ⇒ generic rejection.
    - Timing: client records mount time; a submission faster than 2.5s, or
      with an implausible timestamp, ⇒ generic rejection. (Verified: a ~3s
      genuine fill is NOT rejected; a honeypot-filled submission IS.)
    - Safe errors: users see short, non-technical messages only. No stack
      traces, adapter/provider names, upstream response bodies, or secrets
      reach the browser. Server logs carry status codes / error names only —
      never form content.

No CAPTCHA was added (not warranted).

8. STRUCTURED-DATA DECISION
================================================================================

DECISION: schema.org/Organization with a ContactPoint. NOT MedicalBusiness,
NOT LocalBusiness.

Rationale:
    - MedicalBusiness would misrepresent Zenward as a medical-services
      provider; it is a non-emergency transportation company.
    - LocalBusiness implies a verified, published physical premises and
      typically address / openingHours — none are confirmed for public use.
    - Organization accurately states only what is verified.

Emitted fields (homepage JSON-LD): name ("Zenward Mobility"), description,
url (NEXT_PUBLIC_SITE_URL), logo, areaServed (State: Georgia), and
contactPoint { telephone +14702068005, contactType "customer service",
areaServed "US-GA", availableLanguage "English" }.

NOT emitted: address, openingHours, aggregateRating, priceRange, license,
partner/affiliation data.

Recorded in docs/product/marketing-scope.md ("Structured data").
Verified in the served HTML.
