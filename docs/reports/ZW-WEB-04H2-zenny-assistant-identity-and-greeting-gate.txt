3. ARRIVAL SOUND
----------------
src/lib/assistant/chime.ts. Native Web Audio API, no audio file, no
library, no external URL, no network, no voice. Two soft sine notes, E5 659
Hz then A5 880 Hz, gentle attack and decay, ~0.55 s, peak gain 0.2 (~20%).
Played AT MOST ONCE per page lifecycle, when the teaser FIRST appears
(launcher effect guarded by a ref). Never on panel open/reopen, replies,
validation errors, phone delivery, quote clicks or later in-site
navigation; never on form pages (no teaser there). Supplemental only: no
screen-reader announcement and nothing depends on it.


4. AUTOPLAY FALLBACK
--------------------
Browser policy respected: if the browser reports no prior user activation
(navigator.userActivation.hasBeenActive === false), nothing is created (no
AudioContext, so no autoplay console warning). Where that API is missing it
tries once and quietly closes a context that isn't allowed to run. Never
throws, logs, retries or bypasses protection; the teaser never waits on
it. In practice a fresh first page load is silent (Zenny appears visually),
and the chime is heard when the teaser first appears after the visitor has
interacted (e.g. arrived on a form page, then navigated).
QA (instrumented AudioContext): fresh load -> 0 contexts, teaser shown,
console clean. Interact on /contact, navigate home -> 1 context, 2
oscillators. Phone step + reply + reopen + navigate -> still 1/2 (no
repeat). 0 external requests.

8. CONTACT-DELIVERY IMPLEMENTATION
----------------------------------
Smallest safe server-side path, reusing the existing trusted contact
delivery:
  src/lib/contact-intake/types.ts    + AssistantCallbackInput { phone },
                                       AssistantCallbackResult { delivered }
  src/lib/contact-intake/adapter.ts  + submitCallback() on the existing
                                       ContactIntakeAdapter:
      stub (repo default)  -> { delivered: false }, sends nothing
      email (production)   -> one Resend email to CONTACT_INTAKE_EMAIL,
                              server-only credentials; delivered:true ONLY on
                              a 2xx; failures log status/error name only,
                              never the number
    + buildAssistantCallbackText() (pure, tested)
  src/app/assistant/actions.ts       "use server" submitAssistantCallback:
      accepts EXACTLY { phone } (any other key -> rejected, not trimmed),
      re-validates the number server-side, applies the existing anti-bot
      timing guard (src/lib/forms/guard.ts; min 2.5 s since the panel
      opened), never logs the number, never throws to the client.
Browser -> Server Action -> contact adapter -> Resend. The number is never
sent from the browser to a third-party API; no credentials reach the client.
Client flow: one attempt on Continue (button disabled while sending; no
automatic retry). The number is then cleared from component state; the
launcher keeps only an in-memory "phone step done" flag (no number), so a
same-session reopen doesn't ask again; a reload resets.
  Delivered      -> "Thank you. How can I assist you today?" + quick
                    actions + chat input. The number is not echoed.
  Not delivered  -> "I couldn't save your number for follow-up, but you can
                    still use Zenny below." + "Call Zenward 678-935-5489" +
                    quick actions + chat input. Zenny stays fully usable;
                    no fake success.
  Never says an operator will call, a callback is scheduled, or anything
  definite.
