4. SENSITIVE-DATA RULES
==================================================
A Google-facing conversion carries ONLY one click identifier (gclid | gbraid | wbraid),
the conversion action and the conversion time.

Never sent:
- serviceType, service label or slug
- names, relationship, phone, email
- pickup, destination, date, time, return trip, recurring schedule
- assistance level or notes, additional notes, airport/flight details
- integration, idempotency, organization, tenant, Request, Passenger or Trip IDs
- page URL, path, query, title, referrer
- any context object

Enforcement:
- buildClickConversion takes only the event NAME, so no event fields can reach it.
- Its output is a fixed shape (tested with every forbidden field supplied as input).
- The internal event layer is unchanged: serviceType is still never an event parameter.

==================================================
5. HEALTH / SERVICE URL RISK (critical finding)
==================================================
A conventional browser Google tag (gtag.js / the Google tag) reports, as part of its OWN
requests:
- the current page URL, INCLUDING the query string
- the referrer
- the page title, for page-level hits

It does this on every page where it runs, and on conversion hits. Removing custom event
parameters does NOT prevent it. With such a tag, Google would observe that an ad-click
visitor viewed:
- /services/dialysis-transportation
- /services/wheelchair-transportation
- /metro-atlanta/dialysis-transportation
- "Dialysis Transportation in Metro Atlanta" (the page title)

A conversion on /request-transportation?service=dialysis would carry "service=dialysis".
The tag would also set first-party advertising cookies site-wide.

Partial mitigations (page_location/page_referrer/page_title overrides, stripping
?service= via history.replaceState, limiting which pages load the tag) each need
network-level verification and do not stop the tag running and observing navigation.

FINDING: a browser Google tag is not acceptable for Zenward unless owner/legal explicitly
accept that exposure. This is treated as a BLOCKER for options A and B.

==================================================
6. ATTRIBUTION ARCHITECTURE OPTIONS
==================================================
| Option | Attribution | Exposure | Verdict |
| --- | --- | --- | --- |
| A. Site-wide Google tag | best | high | rejected (§5) |
| B. Tag only at conversion time | largely lost | medium | rejected |
| C. First-party click-ID capture + server upload | good same-visit | low | recommended |
| C′. Nemryn-owned upload | best (confirmed trips) | low | future; needs an intake contract change |
| D. Manual offline import (CSV) | as C | low | fallback if API access is delayed |

Details:
- A: conventional attribution, but every page URL, query, title and referrer goes to
  Google, plus ad cookies on all pages.
- B: the gclid lands on the landing page with nothing to record it. When the tag loads
  later on the request page the URL no longer carries it, so attribution falls back to
  Google's unreliable cross-site signals. The conversion hit still exposes the
  request-page URL (?service=…).
- C: Google receives only the click ID, the action and the time. No browser Google code,
  so no URLs, titles, referrers or browsing. Needs Google Ads API access (OAuth +
  developer token) on the server, no new browser processor, and no Google cookie.
- C′: upload when the trip is actually confirmed. Requires carrying the click ID into
  Nemryn, which is a Website Intake contract change and not allowed now.

==================================================
7. RECOMMENDED ARCHITECTURE
==================================================
Recommendation: C, a server-side click conversion upload with first-party click-ID
capture. The click ID is kept for THIS VISIT ONLY (sessionStorage) as the starting
point; a longer first-party cookie is a separate consent decision.

Flow:
  ad click with auto-tagging → landing URL ?gclid / gbraid / wbraid
  → parseClickId keeps one ID (approved storage)
  → request submitted
  → Server Action: intake delivered:true
  → buildClickConversion
  → Google Ads uploadClickConversions, fire-and-forget

Constraints:
- The click ID never enters TransportationRequestInput, the Nemryn body, notes, events
  or the assistant.
- No browser Google script or cookie.
- Phone clicks are not uploaded.
- The provider enquiry can use the same path from the contact Server Action, under its
  own action.

Priority check:
1. Health context protected: yes, Google sees no page context.
2. Measures delivered requests: yes.
3. Attribution: good within the visit; a cookie extension is possible.
4. Processors/cookies: no Google cookie; Google Ads API only.
5. No analytics stack.

Owner/legal input is required before implementing capture: it is persistence plus
sharing an identifier with Google after a health-adjacent request.

8. GOOGLE ADS ADAPTER CHANGES
==================================================
New src/lib/analytics/google-ads.ts, pure, with:

  future browser-side signal. It returns null unless active, passes only the conversion
  key, sends the primary at most once per page, and swallows all errors.

New src/lib/analytics/conversions.ts: the classification table.

Design boundaries:
- registerAnalyticsSink stays the browser integration boundary, and it is still
  registered nowhere.
- Components keep emitting internal events only.
- Nothing imports either new module, so they are unreachable and tree-shaken.

Also changed (duplicate protection, see §19): RequestTransportationForm and ContactForm.

19. DUPLICATE-CONVERSION PROTECTION
==================================================
| Scenario | Outcome |
| --- | --- |
| Success re-renders | The event fires from the submit handler, not render or effects, so it never re-fires. |
| React Strict Mode | It double-invokes renders and effects, not event handlers, so no duplicate. |
| Retry after failure | The same submissionId; the conversion fires only on the delivered attempt. |
| Back navigation / refresh | A fresh mount with a fresh submissionId, and no success state is restored, so no re-fire. |
| Idempotent intake replay | Nemryn returns 200 {ok:true} for a replay, so the browser would count it again; the once() guard below prevents that. |

DOUBLE-CLICK — a real gap was found and fixed. The quote form's guard read `status` from
the closure, so two clicks in the same frame, before React re-rendered, could both
submit. The second goes to Nemryn as an idempotent replay (no duplicate request) but would
have emitted transportation_quote_submitted twice. The contact form had NO in-flight
guard, so it could send two messages and count two provider enquiries.

Fixes (no payload or semantics change):
- RequestTransportationForm:
  - a synchronous inFlight ref guard
  - the conversion now fires through markSubmitted = useRef(once(...)): at most once per
    mount, i.e. per submissionId
  - still behind isDeliveredConversion
- ContactForm:
  - a synchronous inFlight ref guard (reset in finally)
  - provider_enquiry_submitted at most once per mount
- Google-side: the server upload should run only in the delivered branch of one Server
  Action call, and createConversionSink sends the primary at most once per page.
- The intake idempotency key stays authoritative for operations and is NOT sent to
  Google.

20. CAMPAIGN ATTRIBUTION FINDING
==================================================
- With auto-tagging, Google appends gclid (or gbraid/wbraid on iOS app/web flows) to the
  landing URL. UTM parameters appear only if added to final URL suffixes.

  next page, so attribution is lost after the landing page. This is why capture is
  required for C.
- The 04D campaign pages link to /request-transportation?service=<value> without

  needed.
- Not done (tested): click IDs and UTMs are not added to Nemryn data, notes, the
  assistant or analytics events.
- For the approved implementation, documented in conversion-measurement.md §6:

  | Item | Value |
  | --- | --- |
  | Identifiers | one of gclid/gbraid/wbraid; no UTMs |
  | Storage | sessionStorage, this visit, recommended (a cookie up to 90 days is the consent alternative) |
  | Deletion | when the tab closes (sessionStorage) or on expiry; cleared after upload |
  | Consent | per legal |
  | Server visibility | sent beside the request to Zenward-Web's Server Action only, then to Google Ads |
