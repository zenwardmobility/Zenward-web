2. ASSISTANT SCOPE
------------------
A website concierge for guidance and routing. It does:
  - welcome visitors and explain what Zenward does
  - explain the eight services (each with its canonical summary)
  - help identify the right service (typed text or guided buttons)
  - explain wheelchair-accessible, Airport and recurring transportation
  - explain the request process, request ≠ confirmed ride, and the 2-hour
    response standard
  - share the approved 04F trust facts
  - give the phone number and route to service pages, the quote form (with
    the service preselected), Contact and Healthcare Providers
It never: checks availability, quotes or calculates prices, books, confirms,
reschedules or cancels, looks up requests or passengers, calls Nemryn or any
CRM, creates entities, dispatches, promises pickup times, gives medical
advice, takes payment, or implies a person is chatting.


3. PUBLIC NAMING
----------------
"Zenward Transportation Assistant" (panel title). The welcome text is
exactly as briefed: "Hi, I'm Zenward's Transportation Assistant. I can
help you choose a transportation service, understand how requests work, or
get in touch with our team." Launcher: Zenward symbol + "Need help?"
(accessible name "Open the Zenward Transportation Assistant"). No human
name, no portrait, no robot or sparkle icon. Only the locked Zenward symbol
SVGs are used. A standing note under the title is honest about what it is:
"I share general information and can't see or change bookings. To talk to
our team, call 678-935-5489." No "AI", "chatbot", "agent", "manager" or
"dispatcher" anywhere in public copy (test-enforced).

6. LAUNCHER / PANEL UX
----------------------
Launcher: 48px-tall pill, bottom-right (16px phones / 24px sm+), respects
env(safe-area-inset-bottom), white with soft shadow; hidden while the panel
is open; focus returns to it on close. On /request-transportation it is
hidden below 1024px and collapses to the 48px symbol from 1024px (see §25).
Panel: non-modal dialog (role="dialog", aria-modal="false", labelled by
the title). Phones: a bottom sheet, max 80dvh (measured 80% at 390, 74% at
430), the page stays visible above it. sm+: a 380px floating panel,
bottom-right, max 40rem. Care Navy header with the inverse symbol, close
button, honest note, scrolling conversation (internal scroll), input pinned
at the bottom. Opening focuses the panel title (not the input, so phones
don't pop the keyboard). Escape closes it from anywhere, and so does the
close button. Following any in-site link closes it.


7. QUICK ACTIONS
----------------
Start: Request transportation · Which service do I need? · Wheelchair
transportation · Recurring transportation · Airport transportation · Talk
to Zenward.
"Which service do I need?" shows 4 choices (Doctor or clinic visit,
Dialysis, Therapy or rehab, Leaving the hospital) + "More options" (Trips
that repeat, An older adult's medical trip, Wheelchair accessibility,
Airport trip, Something else: Request a Quote). Never all eight at once.
After a service: Request <Service> (primary) · Learn about <Service> ·
Choose another service. Follow-up buttons show only under the latest
reply. Links and phone actions stay usable in earlier replies.


8. NATURAL-LANGUAGE INTENT ROUTING
----------------------------------
Deterministic: text normalised (lowercase, punctuation stripped, max 500
chars), then bounded keyword patterns. Precedence:
emergency -> status/changes -> provider -> services -> topics (coverage,
pricing, credentials, process, trust, response time, hours, availability,
area, medical, contact, thanks, greeting, general transport) -> sensitive-
only -> unknown. No general conversation, no model.
Verified phrases (tests): ride to my doctor -> Medical Appointment;
dialysis three times a week -> Dialysis + recurring tip; wheelchair ride ->
Wheelchair; ride from the airport -> Airport; hospital is discharging my
mother -> Hospital Discharge; therapy appointments every week ->
Rehabilitation + recurring tip; senior transportation -> Senior Medical; I
need a ride every Monday -> Recurring Care; I need an ambulance now ->
emergency; how much? -> pricing; where is my request? -> status; are you
insured? -> Licensed & Insured; are you always on time? -> punctuality
standard.


9. SERVICE SELECTION
--------------------
One service: "Zenward provides <Label> in Metro Atlanta. <canonical
summary>" + one tip + "I can take you to the quote request with <Label>
selected." Two services (disambiguation, max two): both offered as
Request buttons. When wheelchair is one of them it leads, per the brief:
"Zenward provides both Dialysis Transportation and Wheelchair-Accessible
Transportation in Metro Atlanta. If wheelchair accessibility is the key
transportation need, I can open the request form with Wheelchair-Accessible
Transportation selected, and you can note the dialysis details in the trip
notes." A generic "doctor/clinic" mention is dropped when dialysis or
rehab is named. No diagnosis, no inferred conditions.


10. QUOTE-FORM HANDOFF
----------------------
Only /request-transportation?service=<serviceType>, taken from
SERVICE_CATALOG[slug].requestHref (or the plain /request-transportation).
isAllowedHref permits exactly one query key, `service`, with an
allow-listed value. Anything else (name, pickup, date, &extra, #hash,
"other", unknown slugs, external URLs) is rejected (tested). No
localStorage or URL state carries request data. Browser-verified at all
widths: "Request Dialysis Transportation" -> /request-transportation
?service=dialysis with Dialysis preselected in the 04G form; panel closed.


11. EMERGENCY HANDLING
----------------------
Detected first and deterministically (also in safeRespond, before any
future provider): 911, ambulance, "emergency" (but not "non-emergency"),
chest pain, can't/not breathing, unconscious, collapsed, overdose, severe
bleeding, "having a stroke/heart attack/seizure", suicide wording ("rehab
after a stroke" is not an emergency, tested).
Reply: "Zenward provides non-emergency transportation. If this is a medical
emergency, call 911 or your local emergency service." + "Zenward doesn't
provide ambulance or stretcher transportation." Actions: Call 911 (tel:911)
and "This isn't an emergency". No service or quote links. No medical
instructions.


12. HUMAN HANDOFF
----------------
Call 678-935-5489 (business.phoneHref), Send a message (/contact),
Healthcare providers (/healthcare-providers), Request a Quote. Never "an
agent will join". The panel note says it can't see or change bookings.


13. PRICING
-----------
"Pricing is confirmed after Zenward reviews the transportation request and
trip details." + not-a-booking line; Request a Quote + Call. No estimates,
no currency amounts (validator bans "$<digit>"). Coverage (Medicaid,
Medicare, insurance) is a separate honest reply: "I can't confirm payment
or coverage options here. Please call..." (never "we accept").


14. REQUEST-STATUS HANDLING
---------------------------
"The Transportation Assistant can't view request status yet. Please call
Zenward at 678-935-5489 for help with an existing request." Also for "was
my request accepted / is my booking confirmed". Cancel/reschedule/change:
"I can't change or cancel a trip here. Please call...". Nothing is queried.


15. TRUST RESPONSES
-------------------
Only 04F facts, quoted from trust.ts: licensed & insured; "Punctuality is
our standard. Trips are planned around pickup and appointment times.";
trained and vetted drivers with background checks; patience, dignity and
compassion; 2-hour response during working hours. Questions about CPR,
first aid, ADA, certification, drug testing, licence numbers or policies
get: "I can't confirm specific certifications or programs here." + the
approved facts + call (never affirmed; tested). Hours: the briefed
"aren't published here yet" answer; "24/7" questions route there too.


16. AIRPORT HANDLING

/request-transportation?service=airport_transportation. No flight
tracking, meet-and-greet, baggage, escort, permit or 24/7 claims
(validator + test). "Do you track flights?" gets the Airport service
answer without affirming tracking.


17. WHEELCHAIR HANDLING

Canonical summary + the existing hub wording ("Tell us about the

18. CONVERSATION STATE / PRIVACY

The conversation lives in the panel component's memory only. Closing the

19. SENSITIVE-DATA HANDLING
---------------------------
Detected (never stored): phone numbers, emails, street addresses,
month/day dates, clock times, "my/his/her name is", medical terms
(diagnoses, medications, DOB). Then the reply leads with: "For your
privacy, and to make sure the transportation team receives those details
correctly, please use the secure Request a Quote form rather than this
chat." with "Continue to Request a Quote" (service-only link if a service
was recognised). Replies never echo the visitor's text (tested with a
unique token, an address, a phone number and an email).

21. FUTURE AI-PROVIDER BOUNDARY
-------------------------------
provider.ts defines `AssistantProvider { id; respond(input, ctx) }` and
`deterministicProvider` (the only one used). `safeRespond(provider, ...)`
keeps emergency handling deterministic, runs the provider, and falls back
to the deterministic reply if the provider throws or its reply fails
`validateReply` (canonical links only, ?service= only, approved claims
only). Tested with a provider that returns "Your ride is confirmed." and a
leaky link, and with one that throws.
Activation path (NOT done; needs owner + legal decisions, privacy-policy
update, vendor DPA and credentials):
  1. Server-only provider behind a Server Action or route handler, key in
     server env, never NEXT_PUBLIC_.
  2. Send only the current message + knowledge.ts facts. No transcripts,
     no request/passenger data, no Nemryn.
  3. Constrain output to AssistantReply JSON and pass every reply through
     safeRespond/validateReply.
  4. No logging of message content; disclose the processor in /privacy.
No API key was invented and no SDK was added.
