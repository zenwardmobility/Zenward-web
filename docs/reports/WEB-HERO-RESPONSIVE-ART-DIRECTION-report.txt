================================================================================
1. ROOT CAUSE
================================================================================

The desktop hero was a single full-bleed `next/image` (`fill` + object-cover)
covering the entire <section> at every viewport width. The section height was
governed by a near-fixed min-height (~40rem) plus content, so it stayed ~640–720px
tall regardless of width.

Consequently the effective container aspect ratio for the 1.79:1 (16:9) source
changed drastically with viewport width:

    1280 wide / 720 tall  ≈ 1.78:1   (fine — matches the source)
    1920 wide / 720 tall  ≈ 2.67:1   (crops ~33% off top + bottom)
    2048 wide / 720 tall  ≈ 2.84:1   (crops ~37%)
    2048 wide / 835 tall  → hero pinned near ~640–720 → ~3.0:1 → heads and the
                             wheelchair get cut; the ramp is squeezed out

object-cover has no choice but to zoom in and slice the photo. object-position
alone cannot fix it — moving the crop window around a too-tall-for-the-frame
image just trades one lost subject for another. The photo was also being
stretched across 2560px of viewport from a ~1376px source.

3. NEW BREAKPOINT STRATEGY
================================================================================

Four deliberate hero modes, keyed to viewport class:

    A. MOBILE            < 1024px  portrait crop, full-bleed, vertical scrim
                                   (< lg; 768–1023 is a legitimate
                                   art-directed "portrait on a tablet" band —
                                   it is NOT a scaled desktop)
    B. COMPACT DESKTOP   1024–1279 landscape crop, full-bleed, its OWN
                                   object-position (object-[66%_40%]) and a
                                   trimmed vertical rhythm (py-3xl, not py-4xl)
    C. NORMAL DESKTOP    1280–1599 landscape crop, full-bleed, the existing
                                   premium composition (object-[74%_42%],
                                   py-4xl) — kept because it already works
    D. ULTRAWIDE         ≥ 1600px  landscape crop is NO LONGER full-bleed. It
                                   becomes a right-anchored region ≈ 62vw wide,
                                   capped at 82rem (≈1312px, below the ~1376px
                                   source so it is never upscaled). Care Navy
                                   fills the space to its left; a broad
                                   navy→transparent dissolve overlaps the
                                   region's own left ~half so there is no seam:

                                     | NAVY / CONTENT | GRADIENT | PHOTOGRAPH |

Only one <Image> is in the layout per breakpoint (CSS `lg:hidden` /
`hidden lg:block`), and each `sizes` string now reflects the real coverage so
the preload scanner never fetches an inactive or oversized crop.

================================================================================
8. ULTRAWIDE IMPLEMENTATION  (≥ 1600px)
================================================================================

The photo layer stops being `inset-0` and becomes a capped, right-anchored
region:

    <div className="absolute inset-y-0 right-0 -z-10 hidden w-full lg:block
                    min-[1600px]:w-[62vw] min-[1600px]:max-w-[82rem]">
      <Image … className="… min-[1600px]:object-[56%_36%]" />
      <div className="… min-[1600px]:block" style={SCRIM_ULTRAWIDE} />
    </div>

  - width: 62vw, capped at 82rem (~1312px). The Care Navy <section> background
    fills everything to the left. At 1600 the region is ~992px; at 1920 ~1190px;
    at ≥ ~2120px it is pinned at ~1312px and navy fills the rest.
  - never upscaled: 82rem < the ~1376px source width, and `sizes` (below)
    tells next/image the true coverage so it serves at most the native crop.
  - object-[56%_36%]: at these region aspect ratios object-cover crops only
    lightly; 56% keeps the van + seated passenger + staff centred, 36%
    protects the staff member's head near the top.

SCRIM_ULTRAWIDE (relative to the region, not the viewport):

    linear-gradient(to right, NAVY 0%, NAVY 12%, mix72 30%, mix30 46%, transparent 64%)

  Solid navy at the region's left edge → a seamless join with the navy field
  to its left (no dark-rectangle / image-rectangle boundary). Dissolves across
  the region's left ~half, so the headline stays readable where the two meet
  and the van "emerges" from the navy. The region's right ~36% is fully clear.

Because the region ≈ the source aspect, there is no excessive vertical crop at
any ultrawide width, no enlargement/upscaling, and the hero never looks
stretched or visually empty (navy + the Route Teal lower-left glow + the
content grid fill the left side).


================================================================================
9. HERO HEIGHT STRATEGY
================================================================================

Discrete, viewport-classed min-heights instead of one large fixed value:

    base            min-h-[33rem]   (528px)
    sm (≥640)       min-h-[36rem]   (576px)
    lg (≥1024)      min-h-[38rem]   (608px)   + py-3xl
    xl (≥1280)      min-h-[40rem]   (640px)   + py-4xl
    ≥1600           min-h-[42rem]   (672px)

In practice the content block (headline + copy + 2 CTAs + audience line) plus
padding plus the banner-clearance strip make the desktop hero ~688px at 1024
and a steady ~720px from 1280 up — so it is never shallow on ultrawide (the
old failure) and not gratuitously tall on a compact laptop. The ultrawide
photo region is `inset-y-0` of that height, and its width (62vw / 82rem) is
chosen so the region aspect tracks the ~1.79:1 source rather than the
viewport.


================================================================================
10. IMAGE-REGION SIZING STRATEGY
================================================================================

    < 1600px   image = 100% of the hero (full-bleed)
    ≥ 1600px   image region width = clamp( , 62vw , 82rem )
               · 1600 → ~992px   (≈ 62vw)
               · 1920 → ~1190px  (≈ 62vw)
               · 2048 → ~1270px  (≈ 62vw)
               · 2560 → ~1312px  (capped at 82rem ≈ 51vw; navy fills ~49vw)

82rem cap = ~1312px < the ~1376px native source ⇒ the region never asks for
more pixels than exist, so the photograph is never upscaled (task §13).


================================================================================
11. GRADIENT STRATEGY
================================================================================

Three named scrims, each its own absolutely-positioned layer — the gradient
never touches, blurs, or filters the photograph:

    SCRIM_PORTRAIT   (< lg)      vertical, top-and-bottom heavy
    SCRIM_FULLBLEED  (lg…<1600)  horizontal, solid left → clear by ~82%
    SCRIM_ULTRAWIDE  (≥1600)     horizontal, relative to the right-anchored
                                 region: solid at the region's left edge
                                 (seamless join with the navy field),
                                 dissolving across the region's left ~half

Plus the unchanged shared layers: a restrained Route Teal lower-left radial
(brand character) and a short bottom fade into the next section. No blur, no
`backdrop-filter`, no whole-image opacity, no hard seam at any width.

================================================================================
14. PRELOAD / PERFORMANCE CHANGES
================================================================================

Reviewed the two-priority-<Image> setup. Kept it (it is the cleanest
Next.js-native art-direction approach that preserves per-crop AVIF/WebP +
srcset); a raw <picture>/<source> would have forfeited Next's optimizer.
Redundant-preload behaviour is contained by the `sizes` placeholder trick:

  Verified in the served HTML — two <link rel="preload" as="image">:
    mobile  imageSizes="(min-width: 1024px) 1px, 100vw"
    desktop imageSizes="(min-width: 2120px) 1312px, (min-width: 1600px) 62vw,
                        (min-width: 1024px) 100vw, 1px"
  On a phone the desktop preload resolves to the 1px branch → the scanner
  fetches only the smallest (~640w, ~20 KB) desktop candidate, not the full
  image; on desktop the mobile preload does likewise. No inactive full-res
  fetch.

  Served desktop crop (AVIF, q90), native cap 1376×768:
    w=1080 → ~47 KB     w=1200 → ~54 KB     w≥1920 → ~67 KB
  LCP asset stays well within budget; no upscaled bytes are ever produced.
  No layout shift (section min-heights + `fill`); no animation dependency.
