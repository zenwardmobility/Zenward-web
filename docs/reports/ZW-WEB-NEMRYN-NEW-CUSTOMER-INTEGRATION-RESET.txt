3. CODE VS ENVIRONMENT
==================================================

The Nemryn connection is ALREADY fully environment-driven. No tenant-specific
value is hard-coded, so the adapter was NOT rewritten and no new abstraction
was added.

The OLD connection exists only as Vercel environment values. Per the prior
deployment report, Vercel Production is expected to hold:

  REQUEST_INTAKE_MODE              = platform
  PLATFORM_INTAKE_URL              = <redacted — Nemryn public intake URL>
  PLATFORM_INTAKE_INTEGRATION_ID   = <redacted — old integration id>
  PLATFORM_INTAKE_ORIGIN           = expected UNSET (optional)

These were NOT read or modified (no Vercel access used). The owner should
confirm the actual values in the Vercel dashboard.

To put production in the UNLINKED state, the owner would either:
  (a) remove PLATFORM_INTAKE_INTEGRATION_ID (platform mode then fails closed),
      or
  (b) set REQUEST_INTAKE_MODE=stub / remove it (unlinked adapter).
Both are now safe (section 5). Until the owner does one of these, a
deployment keeps using the old integration id. If that integration has been
disabled in Nemryn, Nemryn returns a generic 400 and the visitor sees
"We couldn't submit your request... or call us". That is also fail-closed,
not a false success.

==================================================
4. SERVER-SIDE BOUNDARY
==================================================

- All intake configuration is read with process.env inside the server-only
  adapter. None of it is NEXT_PUBLIC_.
- The Server Action is the only thing the browser can call. It rejects any
  caller-supplied organization/tenant field at any depth, and the adapter
  re-checks the outgoing body for tenancy keys (defence in depth).
- No database client, Supabase client, service-role key, RPC or organization
  UUID exists anywhere in the repo.
- Nemryn resolves the owning organization from the opaque
  integrationExternalId server-side. Zenward-Web has no tenant branch.

5. UNLINKED BEHAVIOR
==================================================

FINDING (fixed): with no integration configured (REQUEST_INTAKE_MODE unset,
"stub" or unrecognised, which is the repo default), the old stub adapter
returned { ok: true, delivered: false }. The form then showed a green
"Request received — We have your details" screen with a reference number,
while the request was delivered and stored NOWHERE. That was a false success
and a silent discard.

NEW behaviour (UnlinkedRequestIntakeAdapter, adapter.ts):
  - returns { ok: false, delivered: false, error: MSG_UNAVAILABLE }
    "Online requests are temporarily unavailable right now. Please call us to
     arrange transportation."
  - the form stays on screen with everything the visitor typed and shows the
    message in its existing role="alert" error slot (no form/UX change)
  - the page's "Prefer to arrange by phone?" Call CTA and the site header
    phone link remain (2 x tel:+16789355489 in the rendered page)
  - no reference number, no "Request received", no request_form_submitted
    conversion event
  - no fetch, nothing persisted; the log line has no request content and no
    variable names:
    "[request-intake] no intake destination configured: request NOT accepted;
     visitor asked to call."
  - no HTTP status, provider name, env variable name or stack trace reaches
    the visitor

REQUEST_INTAKE_MODE=platform with PLATFORM_INTAKE_URL or
PLATFORM_INTAKE_INTEGRATION_ID missing (or a non-https URL) already failed
closed with the same message. Unchanged.

The form's delivered:false success branch (RequestTransportationForm.tsx) is
now unreachable from any adapter. It was left in place so the form stays
unchanged.

Local development note: with no env configured, a local submit now shows the
"call us" error instead of a success screen. This is intentional: there is no
fake-success mode.

6. ACQUISITION READINESS
==================================================

Audit of the current form / action / adapter / mapping:

  utmSource ........ NOT captured
  utmMedium ........ NOT captured
  utmCampaign ...... NOT captured
  utmContent ....... NOT captured
  utmTerm .......... NOT captured
  landingPath ...... NOT captured
  submissionPath ... NOT captured
  referrerHost ..... NOT captured
  formVersion ...... NOT captured

Nothing prohibited is collected either: no IP persistence, full referrer,
full landing URL, cookies, fingerprinting, gclid or fbclid. The only URL
parameter read is ?service= (allow-listed and resolved server-side).

NOT IMPLEMENTED in this pass, deliberately. The only Nemryn contract
available to this repo (docs/architecture/nemryn-trusted-request-intake-
contract.md, frozen at Nemryn c275ec5) defines NO acquisition object, and it
states that Nemryn rejects any body key outside its fixed set. Sending an
"acquisition" key built from a guessed shape could make Nemryn reject EVERY
request with a 400. The brief forbids relying on private Nemryn knowledge, so
the exact published shape must come from the customer-facing contract that
Nemryn shows during "Connect my existing form". That means:
  - the top-level key name
  - per-field types and max lengths
  - the expected formVersion value
  - whether landingPath / submissionPath include query strings (they should
    not)

Once that published contract is in hand, the change is small and fits the
existing seams:
  - browser: capture UTM params + landing path on first page view
    (sessionStorage, try/catch), plus the submission path and the referrer
    HOST only. Pass them as a separate optional argument to the Server Action.
  - Server Action: whitelist + length-cap each field, drop anything else.
  - nemryn-mapping.ts: attach the optional object only when non-empty.
  - tests: allowed-keys test + "absent object when nothing captured".
