================================================================================

`PlatformRequestIntakeAdapter` now POSTs an explicit, versioned envelope
(type: `TrustedIntakeEnvelope` in src/lib/request-intake/types.ts):

  {
    "schemaVersion": "1.0",
    "submissionId": "<uuid>",                 // == Idempotency-Key header
    "submittedAt": "<ISO-8601 UTC>",          // server-generated (adapter)
    "source": "zenward_web",                  // server-generated (constant)
    "request": { ...the 12 validated fields, unchanged... }

Rules enforced on the Zenward-Web side:

    change. New optional `request` fields will NOT bump it.

  - `source` = `"zenward_web"` constant. Never client-set.
  - `submissionId` — see §3.
  - The envelope carries NO organization_id / tenant_id / operator id. The
    endpoint must resolve the Zenward Mobility tenant from its own credentials.
  - The envelope is internal: never exposed to the browser or the visitor.

Verified on the wire (local mock captured every call):

  schemaVersion="1.0", source="zenward_web", submittedAt=ISO

3. IDEMPOTENCY DESIGN
================================================================================

Problem solved: a visitor who submits, hits a network failure, and submits
again must not create two operational requests.

Mechanism (smallest robust approach for this architecture):
  - ONE `submissionId` (UUID v4) per *logical* form submission.
  - Generated in the browser on form mount
    (`crypto.randomUUID()`; if unavailable in a non-secure context it sends
    nothing and the server mints one).
  - Held in a `useRef` and deliberately NOT regenerated on a failed attempt —
    so a user-initiated retry reuses the same id. It is only replaced on a
    fresh page load / component mount (a genuinely new submission).
  - Passed to the Server Action in the `guard` object (`SubmissionGuard`
    gained an optional `submissionId`).
  - The Server Action RE-VALIDATES it (`isUuid()` in src/lib/forms/guard.ts):
    a well-formed UUID is trusted; anything missing/malformed →
    `crypto.randomUUID()` server-side.
  - The adapter sends it BOTH as the HTTP header `Idempotency-Key: <uuid>`
    AND as `envelope.submissionId` (identical values).
  - It is a random UUID — never personal information, never derived from any
    name/phone/email/address.

Retry behaviour (documented and tested):
  | Situation                                   | submissionId | Outcome |
  |---------------------------------------------|--------------|---------|
  | First submit succeeds                       | id-A         | request created; ref shown |
  | Network fails, visitor resubmits (same page)| id-A (reused)| endpoint returns SAME ref; nothing new created |
  | Endpoint accepted but response lost; resubmit| id-A (reused)| idempotent replay → same ref |
  | Visitor reloads and starts over             | id-B (new)   | treated as a new request |
  | Malformed/missing client id                 | server mints | processed normally; retry-dedupe not possible for that one case |

Endpoint obligations (in the Nemryn spec, §7 there):
  - first request for a key → create + persist `key → referenceId` durably
  - same key again → return the SAME `referenceId`, `accepted:true`, HTTP 200
    (or 409 that ECHOES the referenceId — Zenward-Web treats that as success)
  - keep the mapping ≥ 7 days (30 preferred)
  - serialise concurrent duplicates (unique constraint on the key)

Local mock verification (scenario B): two `submit()` calls with the same
submissionId → both `delivered:true`, `referenceId` identical
(`sameReferenceOnRetry: true`).

5. RESPONSE / STATUS CONTRACT
================================================================================

`delivered: true` is returned ONLY on a positive acceptance:
  - HTTP 200 or 201 AND body `{ "accepted": true, "referenceId": "<non-empty string>" }`
  - OR HTTP 409 that ECHOES a non-empty `referenceId` (idempotent duplicate)

Everything else → `delivered: false` (fails closed) + a customer-safe message.

  | Endpoint response                     | adapter outcome     | delivered | visitor message |
  |---------------------------------------|---------------------|-----------|-----------------|
  | 200/201 + accepted:true + referenceId | accepted / duplicate| TRUE      | "Request received…" + reference |
  | 409 + referenceId                     | duplicate           | TRUE      | "Request received…" + reference |
  | 200/201 without accepted+referenceId  | malformed_success   | false     | RETRY message   |
  | 400 / 401 / 403 / 409-no-ref / 4xx    | rejected            | false     | RETRY message   |
  | 429                                   | rate_limited        | false     | UNAVAILABLE message |
  | 5xx                                   | server_error        | false     | UNAVAILABLE message |
  | no response in 10 s                   | timeout             | false     | UNAVAILABLE message |
  | connection refused / DNS / TLS        | unreachable         | false     | UNAVAILABLE message |
  | URL/token missing                     | not_configured      | false     | UNAVAILABLE message |
  | URL not https://                      | insecure_url        | false     | UNAVAILABLE message |

  RETRY message:
    "We couldn't submit your request just now. Please try again shortly, or call us."
  UNAVAILABLE message:
    "Online requests are temporarily unavailable right now. Please call us to arrange transportation."

Neither message contains an HTTP status, a provider/Nemryn name, API
terminology, a token, or tenant information.

`referenceId` requirements imposed on the endpoint (Nemryn spec §8.1):
  - short, human-quotable, safe to display publicly and to log
  - MUST NOT be / contain / be derived from a database key, an organisation
    or tenant id, or a sequential internal id
  - the same idempotency key must always yield the same referenceId
Zenward-Web no longer fabricates a reference: a 2xx with no usable
`referenceId` is now a failure, not a fake success.

11. EXACT NEMRYN IMPLEMENTATION REQUIREMENTS
================================================================================

Full spec: docs/architecture/nemryn-trusted-request-intake-contract.md
Summary of what the Nemryn team must build:

  Transport:      POST, HTTPS only, application/json, respond within ~5 s
                  (hard client abort at 10 s), reject > 64 KB with 413.
  Auth:           Authorization: Bearer <token>; verify first; support 2
                  valid tokens for rotation; 401 on missing/unknown/expired.
  TENANT RULE:    Resolve the Zenward Mobility organisation SERVER-SIDE from
                  the token/config. NEVER read an organization_id / tenant_id
                  / operator id from the request (Zenward-Web never sends
                  one; ignore it if ever present). Enforce tenant isolation
                  at the DB layer with RLS on the created row.
  Body:           the versioned envelope (schemaVersion "1.0", submissionId
                  UUID, submittedAt ISO, source "zenward_web", request{12
                  fields}). Ignore unknown `request` fields; reject unknown
                  major schemaVersion with 400.
  Validation:     defensively re-validate envelope + required fields + enums
                  + own business rules → 400 on failure (don't echo values
                  for public display).
  Idempotency:    Idempotency-Key header (== envelope.submissionId) → create
                  exactly one request; same key returns the SAME referenceId
                  (200), or a 409 that echoes it; persist key→ref ≥ 7 days
                  (30 preferred); serialise concurrent duplicates.
  Success:        201 (new) / 200 (replay): { "accepted": true,
                  "referenceId": "ZW-…" }.
  referenceId:    opaque, short, display-safe, log-safe, NON-sequential,
                  leaks no DB/org/tenant id; stable per idempotency key.
  Errors:         400 invalid · 401 auth · 403 forbidden · 409 duplicate
                  (with ref) · 413 too large · 422 semantic · 429 rate limit
                  (Retry-After welcome) · 5xx server. Bodies may carry a
                  machine `error` string for logs; not displayed by Zenward.
  Logging:        do NOT log the bearer token; treat request names/phone/
                  email and the 4 free-text fields as sensitive PII (redact/
                  hash, minimal). No HIPAA claims.
  Handoff:        provide Zenward-Web ops the URL, the token(s), and a
                  staging instance for an end-to-end test BEFORE
                  REQUEST_INTAKE_MODE=platform is set in production.

12. RISKS / BLOCKERS
================================================================================

  B-1  [BLOCKER — external]  The Nemryn endpoint does not exist. Automated
       request delivery cannot be enabled until the Nemryn team builds it to
       the contract in §11. Owned by the Nemryn team. NOT a launch blocker —
       stub mode + phone fallback remains live and honest.

  R-1  [RISK — low]  Client-supplied `submissionId`. A malicious client could
       reuse one id across different submissions; the only effect is the
       endpoint de-duplicating that client's own requests (self-harm). It is
       re-validated as a UUID server-side; a malformed one is replaced. No
       PII, no injection surface (it is only ever a header value + a JSON
       string the endpoint treats as an opaque key).

  R-2  [RISK — low]  `crypto.randomUUID()` needs a secure context. Production
       is HTTPS so this is fine; the documented fallback (server mints one)
       only loses cross-retry dedup in an already-degraded environment.

  R-3  [RISK — low]  No client/server auto-retry on 429 or 5xx. By design
       (keep it simple, fail closed, phone fallback). A future ZW-WEB phase
       may add one bounded retry. Not a blocker.

  R-4  [RISK — none/operational]  When the endpoint goes live, the referenceId
       shown to the visitor comes straight from Nemryn. If Nemryn violates
       the "no DB/tenant id" rule, an internal id could surface publicly. The
       contract states this explicitly and it must be checked during the
       staging end-to-end test before production cutover.

  R-5  [RISK — low]  `docs/architecture/request-intake-boundary.md` and older
       launch docs still reference "Zenward Platform" / platform-repo section
       numbers in a few places not touched this phase. Cosmetic; align on a
       later docs pass. No functional impact.

  No Supabase, Blob, email-of-request-content, Nemryn code, or new public
  terminology was introduced. tsc / lint / build all PASS.
