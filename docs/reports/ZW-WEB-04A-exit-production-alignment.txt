5. FAIL-CLOSED ADAPTER AUDIT (uncommitted category B)
==================================================================

Why it exists:
  The new-customer integration reset (ZW-WEB-NEMRYN-NEW-CUSTOMER-INTEGRATION-
  RESET, 2026-09-23) prepares Zenward to disconnect from the old Nemryn
  integration and reconnect the way any NEMT customer does. That pass found
  that the UNLINKED state (REQUEST_INTAKE_MODE unset / "stub" / unknown) shows
  a false "Request received" plus a reference number while delivering and
  storing nothing. Going unlinked, even briefly, would silently discard real
  requests, so the unlinked state had to fail closed before any reset.

  Context from the R3 report: on 2026-09-20 production delivered a QA
  request (Nemryn returned 200 {"ok":true}), but it landed in an
  organization that was neither of the two known QA orgs. The owning org was
  never verified. That's the problem the reset addresses.

Files changed:
  src/lib/request-intake/adapter.ts
    - StubRequestIntakeAdapter -> UnlinkedRequestIntakeAdapter; submit()
      now returns { ok:false, delivered:false, error: MSG_UNAVAILABLE }
      ("Online requests are temporarily unavailable right now. Please call
      us to arrange transportation.")
    - removes the stub-only newReference() helper (no other caller; tsc
      clean)
    - one content-free warning log line; no payload, no env names
    - header comments: "CONNECTED, P1-PILOT-S4B-R3" -> "configured per
      deployment; unlinked by default"; "the Zenward Mobility tenant" ->
      "the owning organization"; "No integration value is embedded in this
      source"
  src/lib/request-intake/adapter.test.mjs
    - stub test rewritten: for "stub", unset and "unknown-value" -> customer-
      safe error, no referenceId, /call us/ copy, zero fetch calls, and no
      QA name/phone/notes/env-var names in captured logs
  .env.example (comments only; REQUEST_INTAKE_MODE=stub value unchanged)
    - describes the fail-closed unlinked default; says the integration id
      comes from Nemryn -> Website Requests -> "Connect my existing form";
      ties PLATFORM_INTAKE_ORIGIN to the approved URL entered in Nemryn
  docs/architecture/request-intake-boundary.md
    - stub section rewritten as the fail-closed unlinked state; same
      self-service sourcing of the integration id

Answers:
  Prevents a false "Request received" without real delivery?  YES.
    After the change, the only `ok: true` in adapter.ts is
    `return { ok: true, delivered: true }` (line 194), reachable only when
    Nemryn answers exactly 200 {"ok":true}. Every Server Action early return
    and every other adapter path is ok:false. The form's success screen
    renders only on result.ok, so "Request received" now requires a genuine
    downstream acknowledgement. The conversion event still fires only on
    delivered === true.
    Residual (not a defect today): RequestTransportationForm.tsx still has a
    delivered:false success branch ("We have your details... please also
    call") that no adapter can now reach. Recommend removing it in a later
    intake-scoped change, not in 04B.
  Changes the public Nemryn payload?  NO. PlatformRequestIntakeAdapter and
    nemryn-mapping.ts are untouched; the diff hunks are the stub class, its
    helper and comments.
  Changes service taxonomy?  NO. service-types.ts / services.ts untouched.
  Affects the self-service Nemryn model?  POSITIVELY, and only in docs/
    comments. It removes "CONNECTED"/"Zenward tenant" language and points
    configuration at the same "Connect my existing form" flow any customer
    uses. No runtime coupling is added.
  Tests pass?  YES. 45/45 on the working tree, including "unlinked (stub,
    default or unknown mode) fails closed: no false success, no fetch, no
    content logged".

The change matches the required principle: delivered success only after a
real acknowledgement; unlinked/unconfigured fails safely and directs the
customer to call; nothing is fabricated.

Behaviour difference to note: with no env configured, LOCAL development
submissions now show the "call us" error instead of a success screen. That's
intentional.
