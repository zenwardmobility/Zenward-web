# Zenward Web — Request Intake Boundary

**Status:** Foundation architecture. The `platform` adapter targets Nemryn's production public intake (flat body, `integrationExternalId` + `idempotencyKey`, `{"ok":true}` response). Production is switched to it with `REQUEST_INTAKE_MODE=platform`; `stub` remains the default for local development.
**Last updated:** 2026-09-19 (P1-PILOT-S4B-R3: adapter finalized against the frozen Nemryn contract; the earlier bearer-token/versioned-envelope design is retired).

## Why this exists

This site collects transportation requests and contact messages from unauthenticated public visitors. It must never connect directly to the Zenward Platform's database, expose a service-role credential, or let the browser choose which organization owns a submission — the same security posture the platform repository's own domain model requires of any public-intake path (`ZenWard/docs/product/domain-model.md` §13/§L, decision register ZD-044/ZD-050).

## The boundary

```
Browser (form)
  → Server Action (src/app/request-transportation/actions.ts, src/app/contact/actions.ts)
      — runs server-side only; validates required fields
  → Configured adapter (src/lib/request-intake/adapter.ts, src/lib/contact-intake/adapter.ts)
      — the swappable delivery mechanism
  → [ destination — Nemryn's public intake endpoint in `platform` mode; a safe stub otherwise ]
```

The **Server Action is the boundary**, not the adapter and not the page. The browser never talks to a database, a third-party service, or the Zenward Platform directly — it always goes through the Server Action, which runs exclusively on the server.

## The stub adapter

`REQUEST_INTAKE_MODE=stub` (the default — see `.env.example`; the right value for local development) selects a stub adapter that:

- Validates the submission (the Server Action whitelists fields, normalises and length-caps every string, checks enum values, runs a honeypot + fill-time check) and returns `{ ok: true, delivered: false }` with a locally-generated reference id.
- Persists nothing anywhere. Sends nothing to any external service. Logs no request content (only a mode warning in production). Never touches a credential.

Because it reports `delivered: false`, the success screen tells the visitor to **also call** to confirm, rather than implying a request is queued — and the `request_form_submitted` analytics conversion does **not** fire. This keeps the site honest whenever no trusted intake is configured. The `platform` mode (below) fails closed — selecting it without `PLATFORM_INTAKE_URL` / `PLATFORM_INTAKE_INTEGRATION_ID` returns an honest "please call us" error, never a fake success.

## The platform adapter

Turning delivery on is configuration, not a page/form change — the adapter interface is the seam:

1. `PLATFORM_INTAKE_URL` = `https://app.nemryn.com/api/public-intake/website` and `PLATFORM_INTAKE_INTEGRATION_ID` = the opaque id Nemryn issued (server-only, never `NEXT_PUBLIC_`, never sent to the browser). The id is an identifier, **not** a credential; there is no bearer token.
2. `REQUEST_INTAKE_MODE=platform`.

The call is **server-to-server** (Browser → Server Action → adapter → Nemryn), so browser CORS is not the security boundary for it. A positive acceptance returns `delivered: true`, which flips the success copy and enables the `request_form_submitted` conversion. Every non-acceptance (error status, unexpected success body, timeout, unreachable endpoint) returns `delivered: false` and a customer-safe message.

### What `PlatformRequestIntakeAdapter` sends

`POST` (HTTPS only, no auth header, an `Origin: https://www.zenwardmobility.com` header because Nemryn's integration is origin-locked and fails closed without one, 10 s timeout, one attempt per call) of a **flat** JSON body: `integrationExternalId`, `idempotencyKey`, the requester fields, the **structured** `passengerName`, `serviceType` and (recurring only) `recurringSchedule`, the pickup/destination/date/time/return-trip fields, and the requester's own `assistanceNotes` / `additionalNotes`. Nothing is folded into notes.

- `idempotencyKey` is the form's `submissionId` — one UUID per logical submission, held stable across retries (browser-generated, re-validated or regenerated in the Server Action, never regenerated by the adapter). It contains no personal information.
- The body carries **no** `organizationId` / `tenantId` / `passengerId` / `driverId` / `vehicleId` / `tripId` / `state` / `source`. The Server Action rejects a submission carrying a tenancy identifier and the adapter refuses to transmit one.
- `recurringSchedule` is the *requested* schedule only; a website submission creates no Passenger, Trip, recurring arrangement or assignment — it stops at a pending Request.
- Success is exactly `200 {"ok":true}`. Nemryn returns no Request id or reference, so the site shows a plain "Request received" and no reference number.

The exact field list, response handling and error copy live in **`docs/architecture/nemryn-trusted-request-intake-contract.md`**. Kill switch: Nemryn `request_intake_integrations.is_active = false` disables new website submissions immediately, with no Zenward-Web deploy.

The contact form follows the same pattern (`ContactIntakeAdapter`), but is allowed ordinary email delivery (`CONTACT_INTAKE_MODE=email`, Resend) because it collects no detailed passenger transportation information. `ContactMessageResult` also carries `delivered: boolean` (ZW-WEB-02B): the stub and every failure path return `false`, `EmailContactIntakeAdapter` returns `true` only after a Resend 2xx, and the success screen tells the visitor plainly when a message was **not** sent (and to call) rather than implying it was received.

## What must never happen, at any point

- This site must never hold or use a Supabase (or equivalent) service-role credential for the platform's database.
- This site must never grant itself, or be granted, anonymous SELECT access to any platform table.
- No form on this site ever collects or transmits an `organization_id` / `tenant_id` / operator id, and neither does the server-to-server body — that determination belongs entirely to Nemryn, which resolves it from `integrationExternalId` in its own database and enforces tenant isolation itself.
- The browser must never receive, in any API response, more than a plain acknowledgement (success/failure) — never a reflected copy of platform-internal identifiers, structure, or state, and never an HTTP status, provider name, or token.
- Logs (server-side only) may contain the `submissionId`, a response status category, an error class, and a timeout flag — never request content, never the request body, never the integration id.

## Security boundary summary

This site is a **low-trust public surface** with no standing access to Passengers, Trips, Drivers, Vehicles, Assignments, Memberships, TripNotes, TripEvents, or AuditEvents — now, and after any future adapter swap. If a future integration ever seems to require broader access than "submit one validated request, get back success or failure," that is a sign the integration is being designed wrong, not a sign this rule needs an exception.
